Sensor-to-world fusion for autonomous driving

Learn what camera and LiDAR actually measure, how stereo becomes confidence-aware metric geometry, where calibration ends and registration begins, when each fusion stage is useful, and how a timestamped world state supports planning and safe degradation.

Short answer on the trend

Autonomous-driving vision is not narrowing to 3D detection

Research is moving from isolated, single-frame boxes toward temporal world state: metric geometry, semantics, tracks, maps, occupancy, motion, uncertainty, and several possible futures. Camera-only learned depth and BEV systems improve cost and data scale; LiDAR remains strong direct range evidence; fusion remains the general choice when complementary observability justifies its calibration, timing, compute, and hardware cost. End-to-end models increasingly connect this state to planning, but no one paper is “best” across different sensors, datasets, benchmark versions, latency budgets, and closed-loop protocols.

Study map

Reason through six contracts in order

If the world state is wrong, return to the first violated contract instead of tuning the final planner.

1Measuresensor physics
2Decodeunits + validity
3Aligntime + frames
4Representpoints to BEV
5Fuseevidence + uncertainty
6Operateplan + degrade

Dependency rule: semantics cannot repair an incorrect transform; a learned fusion block cannot recover evidence that was discarded by decoding; a low offline error cannot prove safe closed-loop behavior.

Three-lane data flow

Preserve each sensor’s evidence until it is comparable

The two sensor lanes flow left to right. After their quality gate, follow the bottom lane from right to left into world state and planning.

LiDAR front end

A decoded return is not the raw waveform

Use “raw” carefully: dataset packets and point-cloud messages normally expose firmware-processed returns, not photodetector samples.

Before a point exists

A pulsed LiDAR emits light and receives a time-varying signal. Electronics and firmware perform thresholding or pulse/peak estimation, time-of-flight conversion, multi-return selection, channel calibration, and strength encoding. Only then does a downstream record contain range and beam direction.

Consequence: if only decoded returns are available, downstream software cannot faithfully redo pulse decomposition, recover a return the firmware discarded, or assume vendor “intensity” values are calibrated identically.

Processed-return contract

  • Geometry: range, azimuth, elevation or calibrated beam ID; declared units and axes.
  • Identity: ring/channel, return index or type, packet/frame sequence.
  • Time: per-return acquisition time and clock domain—not only scan publication time.
  • Signal: intensity/reflectivity-like value with its vendor definition, saturation and validity flags.
  • Context: sensor frame, calibration/firmware ID, return mode, temperature or health metadata when available.
Convention: right-handed sensor frame, +z up, azimuth from +x toward +y x = r cos(elevation) cos(azimuth) y = r cos(elevation) sin(azimuth) z = r sin(elevation) point = {x, y, z, strength, ring, return_id, t_acq, validity, frame, calibration_id}

This is one explicit convention, not a vendor-independent default. Apply the sensor’s calibrated beam origins, axes and azimuth/elevation definitions before transforming into the vehicle frame.

Decode before filtering

Reject non-finite, saturated, zero or out-of-range returns with an explicit mask. Never manufacture a valid origin point from an invalid range.

Deskew before merging

A spinning scan observes different points at different poses. Transform each valid return from its acquisition pose to one declared reference time.

Preserve provenance

A geometrically correct XYZ point without its acquisition time, frame, return identity and calibration version is incomplete fusion evidence.

Stereo geometry

Disparity becomes depth only with confidence and units

Rectification reduces correspondence to a scanline. It does not remove occlusion, repeated texture, low texture, glare, calibration error, or range-dependent uncertainty.

Back-project a valid match

d = uleft − uright Z = fxB / d X = (u − cx)Z / fx Y = (v − cy)Z / fy

Use matching units for baseline and output depth. Continue only for finite positive disparity under the declared convention. Keep the source pixel or color so every 3D point can be audited back in the image.

Propagate uncertainty, do not hide it

|∂Z/∂d| = fxB / d² σZ ≈ (fxB / d²)σd σZ ≈ (Z² / (fxB))σd

For roughly constant disparity noise, depth uncertainty grows quadratically with range. A dense far-range cloud can therefore look convincing while containing weak metric evidence.

GateQuestionFailure it catchesOutput policy
NumericIs disparity finite, positive, and above the usable minimum?Invalid match or effectively infinite depthReturn invalid separately; do not clamp into a trusted point.

Current stereo trend: FoundationStereo targets strong zero-shot generalization across domains; Fast-FoundationStereo uses distillation, architecture search, pruning and additional pseudo-labeled data to report more than 10× speedup while staying close to its teacher. Those learned matchers improve the disparity proposal—not the need for metric calibration, occlusion handling, confidence gates or range-dependent uncertainty.

Do not mix the verbs

Calibration, registration, projection, association and fusion answer different questions

OperationQuestion answeredTypical input → outputCommon mistake
CalibrationWhat stable sensor model, extrinsic, or clock offset describes this rig?Many calibration observations → intrinsics, distortion, Tcamera←lidar, time offset + uncertaintyTreating one good overlay as proof across range, time and temperature.
RegistrationWhat transform aligns these particular observations or maps?Two point/image/map sets → estimated relative pose + fitness/conditioningAccepting a low residual on degenerate geometry.
ProjectionWhere does a known 3D point land in a camera?Point + transform + camera model → pixel, depth and validityIgnoring acquisition time, distortion, positive depth, bounds or occlusion.
AssociationDo two observations describe the same object?Projected objects/features + uncertainty → matches, unmatched and ambiguityForcing a nearest match when evidence is incompatible.
FusionHow should compatible evidence update one task or state?Aligned evidence + uncertainty → feature, object, occupancy or belief updateConcatenating stale or miscalibrated evidence without a health path.

Targetless calibration trend · WACV 2026

Learn correspondences, but guard the update

UniCalib maps camera and LiDAR evidence into unified depth representations and predicts probabilistic flow plus reliability. CalibBEV instead aligns modality-specific features in a shared BEV through coarse and refined stages. Both attack the modality gap; neither removes observability, time-alignment, held-out validation, bounded-correction, versioning or rollback requirements.

Two representation decisions

Encode sensor evidence before fusion; expose planner state after fusion

These are different interfaces. An encoder should preserve what a modality measured; the fused state should preserve what prediction and planning must ask.

1 · Modality encoding before or at fusion

EncodingPreserves wellBest fitDominant tradeoff
Points / sparse setsExact sample geometry and per-return attributesRegistration, point-level fusion and sparse point networksIrregular neighborhoods and workload; density changes sharply with range.
PillarsVertical-column statistics in a fast pseudo-imageReal-time BEV detection with efficient 2D convolutionsVertical detail is compressed; cell boundaries and point caps matter.
VoxelsLocal 3D spatial structureSparse 3D detection, segmentation and long-range geometryResolution–memory tradeoff, empty space and center-feature sparsity.
Range imageNative LiDAR beam/ring topologyFast scan-domain filtering and segmentationSensor-view occlusion, wraparound and nonuniform metric footprint.

2 · Fused world state for temporal reasoning and planning

StatePreserves wellBest fitDominant tradeoff
Shared BEV featuresDense learned spatial context in one metric top-down frameJoint detection, mapping, occupancy, prediction and planning headsGrid quantization, memory, calibration coupling and limited direct interpretability.
Objects / tracksCompact semantic identity, pose, velocity and historyInteraction prediction, rules and interpretable modular planningOpen-set obstacles and uncertain free space may disappear behind the object interface.
Occupancy / flowFree, occupied, unknown and time-indexed motionOpen-set obstacles and planner collision/risk queriesGrid resolution, unknown-space policy and probability calibration.

Selection rule: points preserve measurement provenance; BEV supports shared spatial computation; objects are compact and semantic; occupancy is open-set and planner-friendly. A system may retain several interfaces rather than force one universal representation.

Fusion-stage decision

Fuse as early as useful, as late as necessary

Earlier fusion can retain more cross-modal detail; later fusion usually improves modularity, fault isolation and independent validation.

StageMechanism and exampleChoose it whenMain cost / failure test
Point / dataDecorate projected LiDAR points with camera scores, as in PointPaintingA LiDAR detector should reuse camera semantics with a clear geometric interfaceHard projection and sequential errors; perturb time/extrinsics and inspect missing/duplicated evidence.
FeatureAlign deep camera and LiDAR features, as in DeepFusionLocal cross-modal detail matters and joint training/data are availableAugmentation and calibration coupling; ablate learned alignment under drift.
Object / queryLiDAR-seeded or shared queries softly attend to image evidence, as in TransFusionSoft association should replace brittle one-to-one pixel projectionQuery misses and opaque confidence; test camera corruption, sparse range and unmatched objects.
Common BEVEncode each modality into one metric top-down grid, then fuseDetection, map, occupancy and planning benefit from a shared spatial frameQuantization, pooling, calibration and memory; report grid/latency and sensor-dropout ablations.
Late / decisionAssociate boxes, tracks, scores or occupancy beliefs after separate modelsDebuggability, independent redundancy and controlled degradation dominateInformation was already compressed; calibrate scores and retain unmatched/ambiguous evidence.

Two BEVFusion papers

Same name, different work

The MIT/Han Lab paper later published at ICRA 2023 uses optimized camera and LiDAR encoders with a shared BEV for task-agnostic multi-task fusion. The separate NeurIPS 2022 paper by Liang and colleagues emphasizes a camera stream independent of LiDAR and robustness when LiDAR malfunctions. Cite the authors/venue or exact link—never write “BEVFusion proves…” without identifying which paper and protocol.

Runtime sequence

Every cycle has a deadline and a failure branch

1Acquiretimestamp at source
2Decodevalidate metadata
3Synchronizebounded data age
4Deskewone reference time
5Transformone world frame
6Updatestate + covariance
7Planbefore deadline

Sequence invariants

  • A timestamp means a declared event: exposure, row, emission/return, packet receipt, or publication.
  • Interpolation stays inside supported pose history; extrapolation is bounded and flagged.
  • Transforms name source, destination and reference time.
  • State updates retain data age, provenance, uncertainty and missing evidence.
  • Planning consumes a coherent state snapshot and a remaining latency budget.

Failure ordering

  1. Reject malformed or physically impossible samples.
  2. Quarantine stale, mis-timed or unsupported transforms.
  3. Compare cross-modal residuals with each modality’s own health.
  4. Reweight or remove suspect evidence only under an explicit degraded policy.
  5. Request a minimal-risk maneuver when the remaining state cannot support the ODD.

Degraded-state logic

Use hysteresis; one good frame is not recovery

System choice

Camera-only, LiDAR-only, or fusion: “better” depends on the ODD

Compare observability and failure independence before comparing model names.

ChoiceWhy choose itEvidence it contributesRequired stress tests
Camera-onlyLow sensor cost/power, dense semantics, high angular detail and scalable fleet dataAppearance, lane/sign/light semantics, learned or multiview geometryNight, glare, rain/fog, occlusion, metric-depth calibration, viewpoint shift and causal-use ablations.
LiDAR-only perceptionDirect metric range and geometry dominate the task3D surfaces, free-space samples and range in weak illuminationLong-range sparsity, small objects, reflectance, weather, multi-return policy and moving-scan distortion.
Camera + LiDAR fusionComplementary semantics and metric geometry justify hardware and integration costDense class/texture plus direct range, redundancy and cross-checksClock/extrinsic drift, sensor loss, compute/thermal overload, score calibration and safe degraded operation.

Fair ablation: match dataset split, history, maps, labels, external pretraining, parameter/compute budget, post-processing and evaluation protocol. Otherwise the result does not isolate the value of the sensor.

LingBot clarification

LingBot-Map processes streaming monocular images to estimate camera poses and dense scene geometry, which can be accumulated as a point cloud. It is camera-derived reconstruction, not LiDAR and not by itself a detector or driving policy. LingBot-Depth is primarily an RGB-D depth-completion/refinement model; it should not be described as a single RGB camera replacing LiDAR.

What recent work is optimizing

The frontier is broader than box AP: sparse or vector state, temporal stability, occupancy and flow, several trajectory modes, rule/teacher distillation, world-action latent models, reason–action consistency, sensor dropout, latency and closed-loop recovery.

End-to-end bridge

End-to-end describes a training boundary, not the absence of structure

1Evidenceimages + returns
2Shared stateBEV / queries
3Auxiliary taskstracks + map
4Futuresagents + occupancy
5Trajectorymodes + score
6Safetyconstraints + fallback

Modular

Separate perception, prediction and planning interfaces improve fault isolation and targeted validation, but may discard useful task information.

Planning-oriented joint model

Planner loss trains shared state and explicit auxiliary heads. UniAD is end-to-end trainable even though it preserves named tracking, map, motion and occupancy tasks.

Sensor-to-trajectory or action

A shorter learned interface reduces hand-designed boundaries but increases shortcut, data-coverage, dynamics-shift and independent-safety burdens.

Planner-facing contract: carry several plausible futures, probability or confidence, free/occupied/unknown space, data age and health—not only one deterministic box list or one visually plausible trajectory.

Benchmark comparability gate

Ask whether two numbers are allowed to compete

If any material gate differs, report complementary evidence or an ablation—not a winner.

Open-loop warning

On logged nuScenes planning, ego status alone can be surprisingly competitive because the future often follows current velocity and the log does not react to policy actions. This is useful component evidence, not proof that perception is unnecessary.

NAVSIM and Bench2Drive answer different questions

NAVSIM’s planning metric uses a non-reactive simulation of logged actors; Bench2Drive runs a reactive CARLA closed loop. NAVSIM improves on simple trajectory L2, while Bench2Drive adds policy–world interaction and simulator domain gap. Neither result alone certifies real-world safety.

SOTA claim grammar

State the scope in the same sentence

Write “the paper reports the best result on benchmark X, version Y, split Z, with sensors S and training protocol P.” Do not replace that sentence with “model A is the state of the art for autonomous driving.”
