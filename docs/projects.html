Learning outcomes

What every project should teach

01

Technical depth

Derive or implement a meaningful primitive instead of hiding every decision behind a framework call.

02

Experimental discipline

Reproduce a baseline, control variables, report uncertainty, and separate evidence from intuition.

03

Systems judgment

Measure latency, memory, robustness, data quality, maintainability, and degraded behavior alongside accuracy.

04

Failure ownership

Publish an error taxonomy and show how at least one surprising failure changed the design.

05

Reproducibility

Provide tests, exact commands, versions, seeds, data contracts, and an executable evaluation path.

06

Clear explanation

Explain scope, interfaces, alternatives, risks, results, and next experiments in a concise technical review.

Recommended sequence

Grow from a correct primitive to an integrated system

Use the guided builds to learn the workflow; take each longer system study through every gate.

Guided build6–10 hours

Calibration health monitor

Question: can the system detect when a camera model or sensor transform is no longer trustworthy?

Build

Calibrate a camera, project known points, compute reprojection residuals, perturb intrinsics and extrinsics, and design a health threshold with false-alarm analysis.

Required artifacts

  • Coordinate and transform convention.
  • Calibration report with residual plots.
  • Synthetic drift injection and sensitivity curves.
  • Unit tests for projection, inverse, and composition.

Gate: distinguish calibration, correspondence, timestamp, and scene-degeneracy failures.

Guided build8–14 hours

Perspective-to-BEV converter

Question: what information can a planar view transform recover, and where does it become misleading?

Build

Create inverse perspective mapping from calibrated imagery, overlay metric grid cells, test camera-pose perturbations, then compare with depth-aware lifting on non-planar scenes.

Required artifacts

  • Homography derivation and frame diagram.
  • Round-trip and metric-distance tests.
  • Flat-ground, slope, curb, and obstacle cases.
  • Latency, resolution, and memory trade-off.

Gate: label unknown and invalid regions; never present a warped image as metric truth without assumptions.

System study 012–3 weeks

Perception benchmark

Question: when does a global leaderboard metric disagree with the behavior needed in a particular operating domain?

Build

Reproduce a detection or segmentation baseline, validate the evaluator, define critical slices, categorize errors, test one improvement, and quantify accuracy-versus-cost.

Required artifacts

  • Dataset and label contract with leakage audit.
  • Reference metric tests and baseline reproduction.
  • Slice dashboard and qualitative failure atlas.
  • Ablation table with confidence intervals or repeated seeds.

Gate: explain a case where the global metric and the product-relevant conclusion disagree.

System study 022–4 weeks

Real-time edge perception pipeline

Question: can you meet a device budget without silently changing model behavior?

Build

Export and deploy a trained model, validate numerical parity, profile end to end, then optimize precision, shapes, transfers, preprocessing, and post-processing.

Required artifacts

  • Correctness harness across framework and runtime.
  • Latency p50/p95/p99, throughput, memory, and power assumptions.
  • Profiler trace and bottleneck explanation.
  • Accuracy-latency curve and rollback criteria.

Gate: reproduce target-hardware results from one command and explain the dominant bottleneck.

System study 033–4 weeks

Temporal 3D tracking system

Question: how should uncertain, delayed, and occasionally missing measurements become stable state?

Build

Implement prediction, gating, assignment, update, ego-motion compensation, and lifecycle policy. Compare geometric, appearance, and fused association.

Required artifacts

  • State and measurement model derivation.
  • Hand-checked Kalman and assignment unit tests.
  • IDF1/HOTA, velocity, delay, and lifecycle analysis.
  • Occlusion, crossing, timestamp, and dropout stress tests.

Gate: diagnose identity failure as detection, motion, association, lifecycle, or timing—not merely “the tracker failed.”

System study 044–8 weeks

Autonomous-driving systems capstone

Question: can a multi-camera or multi-sensor system turn uncertain measurements into a timely spatial state and a defensible motion trajectory under realistic faults?

Build

Integrate calibration, temporal alignment, camera/LiDAR/radar evidence, localization, BEV or occupancy, tracking, motion prediction, a planning interface, fault injection, and deployment budgets. Compare at least one modular or optimization-based planning baseline with a learned alternative.

Required artifacts

  • Sensor-to-control architecture and coordinate/timing contract.
  • Baseline plus controlled fusion and temporal ablations.
  • Prediction/planning representation contract and collision checker.
  • Sensor-fault matrix, closed-loop scenarios, and degraded-mode behavior.

Gate: trace one failure from sensor time or geometry through perception, prediction, planning, and control; show which monitor detects it and which fallback limits harm.

Experiment standard

Six gates before drawing a conclusion

Time spent is not a gate. Another learner should be able to reproduce the result and challenge the interpretation.

Gate 01

Frame

Problem, consumer, operating domain, metric, budget, risks, and non-goals are explicit.

Gate 02

Reproduce

A known or simple baseline runs from a fresh environment and matches an expected range.

Gate 03

Verify

Core math, transforms, metrics, edge cases, and framework/runtime parity have tests.

Gate 04

Challenge

Slices, counterexamples, perturbations, missing inputs, and failure categories are measured.

Gate 05

Optimize

One hypothesis is tested through a controlled ablation with cost and regression analysis.

Gate 06

Explain

A concise report, demo, reproducible command, comparison decision, and honest limitations are recorded.

Project selection

Choose by the question you want to answer

All six projects are useful; these three branches identify the shortest route to a specific kind of understanding.

Question A · model behavior

How do data and representations change quality?

  • Study data quality, leakage, generalization, long-tail slices, and transfer.
  • Compare frozen, adapted, and task-specific representations.
  • Run controlled ablations with repeated seeds or uncertainty.
  • Use task metrics and failure categories together.

Start with: the perception benchmark.

Question B · computation

Where does runtime actually go?

  • Trace preprocessing, transfers, kernels, post-processing, and queueing.
  • Compare precision, layouts, shapes, batching, and operator fusion.
  • Plot accuracy–latency–memory Pareto frontiers.
  • Explain numerical differences across runtimes and devices.

Start with: the real-time edge pipeline.

Question C · spatial state

How do sensors and time become a 3D belief?

  • Make coordinate frames, synchronization, sensor characteristics, and observability explicit.
  • Compare camera, LiDAR, radar, temporal, and BEV fusion strategies.
  • Inject realistic faults and specify degraded operation.
  • Compare tracks, occupancy, and object-centric representations.

Start with: calibration health, then tracking or the sensor-fusion capstone.

Project review

Questions every conclusion must survive

Technical

  • Which assumption is most fragile?
  • What is unobservable from the selected inputs?
  • Which result did you verify independently?
  • What alternative did you reject, and why?

Experimental

  • What is the simplest baseline?
  • How did you prevent leakage?
  • Which slice contradicts the global result?
  • What would falsify your improvement hypothesis?

Production

  • What happens after the latency deadline?
  • How does the system detect stale or invalid input?
  • What is monitored, rolled back, or degraded?
  • Which cost grows first at 10× scale?
