Bird's-eye-view conversion and perception

BEV is not one transform or one neural architecture. It is a dependency chain from calibrated frames and planar inverse perspective mapping to learned depth lifting, cross-view attention, temporal alignment, sensor fusion, occupancy, and a planning-facing spatial contract.

Prerequisite gate

Do not begin with a network diagram

You must first be able to project a 3D point with named frames, derive a plane homography, back-project a depth pixel, and test calibration/time alignment. Review camera calibration before learned BEV.

Why BEV

A spatial interface for perception

  • A common metric frame simplifies distance, heading, motion, map, and route reasoning.
  • Multiple cameras and range sensors can contribute to the same spatial cell.
  • Temporal features can be ego-motion compensated in a stable coordinate system.
  • Detection, map segmentation, occupancy, flow, and planning can share aligned outputs.

What BEV cannot promise

Representation does not remove ambiguity

  • Monocular pixels do not uniquely determine depth.
  • Occluded or unobserved space remains uncertain.
  • Grid resolution trades detail for memory/compute.
  • Calibration and timestamp errors become spatial feature errors.
  • A ground-aligned grid may poorly represent vertical structure.

Stage 1 · Classical geometry

Inverse perspective mapping on a plane

Use this interpretable baseline for lane/road features and as a geometry oracle for learned systems.

Assume a world/ego ground plane Z = 0 and world-to-camera pose [R | t]. If r₁ and r₂ are the first two columns of R, a ground point maps to a pixel by:

λ [u, v, 1]T = K [r₁   r₂   t] [X, Y, 1]T Himage←ground = K [r₁   r₂   t] [X, Y, 1]T ∼ H−1image←ground [u, v, 1]T

For a dense output, use backward warping: create each BEV cell at metric center (X, Y), map it into the source image with H, divide by homogeneous scale, sample bilinearly, and return a validity mask.

01

Define the grid

Choose forward/side bounds, meters per cell, row/column axis direction, origin, and cell-center convention.

02

Construct points

Create homogeneous ground coordinates for every BEV cell center in the declared ego/world frame.

03

Project

Apply the ground-to-image homography, normalize, and reject points behind/outside the source image.

04

Sample

Bilinearly sample image intensities or semantic probabilities; preserve a visibility/validity map.

Flat-ground failure

Off-plane pixels are placed on the road

Vehicles, people, walls, slopes, crests, and curbs violate the plane assumption. Tall objects stretch away from the camera because their elevated pixels are incorrectly intersected with the ground plane.

Stage 2 · Learned geometry

Lift image features through depth

Lift

For image feature F(u,v), predict a probability or weight over depth bins p(d | u,v). For z-depth d:

Pcamera(u,v,d) = d K−1[u,v,1]T Pego = Tego←camera Pcamera G(u,v,d) = p(d | u,v) · F(u,v)

This creates feature mass along each viewing frustum. Be explicit whether d is optical-axis depth, range, inverse depth, or another parameterization.

Splat

Map each 3D feature sample to a BEV cell and aggregate all cameras/depth bins:

i = floor((X − Xmin) / ΔX) j = floor((Y − Ymin) / ΔY) B(i,j) = Σ G(u,v,d) for samples in cell (i,j)

Sum, mean, max, learned pooling, or sparse scatter have different density and performance behavior. Keep the geometry separately testable from the learned features.

Representation decision

Choose what geometry the task must preserve

There is no globally best point-cloud or BEV representation. Start from sensor topology, vertical detail, range, task output, latency, memory, and deployment kernels; then test the failure mode created by the chosen discretization.

For voxel origin (xmin, ymin, zmin) and cell size (vx, vy, vz):

i = floor((x − xmin) / vx) j = floor((y − ymin) / vy) k = floor((z − zmin) / vz)

Halving all three cell dimensions creates up to eight times as many cells in the same dense volume. Sparse tensors avoid computing empty cells, but coordinate construction, hashing, feature density, and accelerator support still have costs.

Stage 3 · Time and fusion

A BEV map is timestamped, not timeless

Ego-motion alignment

Backward-warp the previous BEV into the current frame using timestamped pose. Validate zero-motion identity, known translation/rotation, validity masks, and grid sampling conventions.

Dynamic objects

Ego alignment makes the static world consistent, not moving actors. Use object motion, temporal attention, flow, recurrent state, or an explicit dynamic representation to avoid ghosts.

Sensor rate and dropout

Camera, LiDAR, radar, and IMU capture at different times/rates. Define interpolation, maximum age, missing-sensor training, confidence, and degraded-mode behavior.

Failure analysis

Diagnose the map by perturbing its assumptions

Extrinsic yaw error

Objects shift laterally with range and disagree across camera boundaries. Inject small rotations and plot cell/box error versus distance.

Camera pitch or height change

IPM lane geometry systematically scales/curves; learned lifting can also drift if calibration is not modeled or trained robustly.

Depth-bin aliasing

Distant features jump between cells or smear. Compare linear, inverse, and task-aware depth bins with memory held fixed.

Temporal timestamp error

Static map edges double under ego motion; moving objects ghost differently. Sweep offset and separate static/dynamic slices.

Camera overlap seam

Cross-view features duplicate or cancel. Audit photometric/domain differences, visibility, calibration, and fusion weights.

Unknown/occluded space

A dense map may look confident where no sensor observed. Preserve observed/free/occupied/unknown semantics and evaluate calibration.
